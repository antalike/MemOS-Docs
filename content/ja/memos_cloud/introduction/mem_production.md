## 1. 機能紹介：なぜ生のメッセージを記憶に加工するのか

MemOS では、あなたが送信するのは **生の情報**（ユーザーと AI の対話、ユーザーの APP 上での操作ログ / 行動軌跡、ナレッジベース文書など）であり、システムが自動的に「記憶化」のプロセスを完了します。

::note{icon="ri:triangular-flag-fill"}
**なぜ記憶加工を行う必要があるのか？**
::

生の情報を単純にすべて保存し、再利用時にそのまま大規模モデルへ渡すだけでは、いくつかの問題が発生します：

- **コンテキストが長すぎる**：生の情報は通常、冗長で大量の重複や無関係な内容を含むため、全体をそのままモデルに入力するとコンテキストウィンドウが著しく長くなり、処理効率が低く Token の無駄になります；
- **検索が不正確**：構造化や抽出を経ていない生テキストは、対話内の重要情報を際立たせにくく、検索時に大量のノイズ内容を誤って再現しやすく、回答品質に影響します；
- **体験が連続しない**：生の対話は一回限りの静的テキストであり、ユーザーの好みや感情、業務背景やルールの変化を認識できないため、継続対話の体験にずれが生じます。

<br>

::note
**MemOS で加工された記憶とは何か？**
::

MemOS は生のメッセージを構造化された記憶ユニットへ変換し、自動的に次を抽出します：

- **重要な事実**：
  - ユーザー対話中の事実情報を抽出します。たとえば「ユーザーは 2025 年の夏休み期間に広州へ旅行する予定である。」；
- **ユーザーの好み**：
  - ユーザー対話中の明示的な好みの表現を抽出します。たとえば「ユーザーは家族旅行が好きだと述べた」；
  - ユーザー対話中の暗黙的な推論パターンを抽出します。たとえば「ユーザーはコストパフォーマンスの高いホテルを好む可能性がある」；
  - MemOS はユーザーの好みのパターンを保持し、後続の回答で一貫性を保つようモデルを導きます。たとえば、ユーザーが AI 支援ライティングを使用する際に「論理が明快な書き方」を示した場合、MemOS は他のタスクでも「論理的なライティング手法」を維持するようモデルを導き続けます。

<br>

**例**：

```json
User: 夏休みに広州旅行を予約したのですが、宿泊ならどんなチェーンホテルがありますか？
Assistant: 【7 Days、Ji Hotel、Hilton】などをご検討いただけます
User: 7 Days にします
Assistant: 承知しました。他にご質問があればまた聞いてください。
```

```json
事実記憶: ユーザーは夏休み期間中に広州へ旅行する予定であり、宿泊先として 7 Days チェーンホテルを選択した。

好み記憶: ユーザーはコストパフォーマンスの高いホテルを好む可能性がある
Reasoning: 7 Days ホテルは通常、経済的で手頃なことで知られており、ユーザーが 7 Days ホテルを選んだことは、宿泊においてコストパフォーマンスの高い選択肢を好む傾向を示している可能性がある。ユーザーは予算制約や具体的なホテルの好みを明確には述べていないが、提示された選択肢の中で 7 Days を選んだことは、価格と実用性を重視していることを反映している可能性がある。
```

> あなたにとって、これは次を意味します：生の対話を保存するだけでよく、自分で「キーワード抽出」や「意図認識」のロジックを書く必要はなく、長期的に呼び出し可能なユーザーの好みを得られます。

<br>

テキスト対話メッセージに加えて、Agent タスク実行の過程に対して、MemOS はツール記憶、スキルにも対応しています：
- **[ツール記憶（tool memory）](/memos_cloud/features/advanced/tool_calling)**：
  - Agent タスク実行過程におけるツール呼び出し情報を記憶として抽出し、ツールの種類、使用シーン、呼び出し結果の特徴を記録して、後続の類似タスクにおけるツールの優先選択に用います。
- **[スキル（Skills）](/memos_cloud/features/advanced/skill)**：
  - ユーザー対話を抽出し、再利用可能な実行能力を生成します。
  - たとえば、「旅行プラン生成」に関する複数ターンの対話から、目的地分析、旅程分解、予算制約を含む実行可能な「旅行プランニングスキル」を抽出します。これは、もはや単に「ユーザーは弾丸旅行が好き」といった、モデル推論の参考用記憶だけではありません。

さらに、MemOS は [ナレッジベース](/memos_cloud/features/advanced/knowledge_base)、[マルチモーダルメッセージ](/memos_cloud/features/basic/multimodal) に基づく記憶加工にも対応しています！

<br>

::note
**記憶はどのように加工されるのか？**
::

MemOS は常に、記憶は静的な記録ではなく、時間とともに進化する対象であり、ユーザーを迅速・正確・継続的に記憶する必要があると考えています。
<br>
記憶の三角問題であるリアルタイム性、正確性、一貫性をよりよく処理するために、MemOS は記憶加工の全プロセスを以下の 3 段階に分割しています：
| 段階 | 目標       | 特徴                                                                 |
| ---- | --------- | -------------------------------------------------------------------- |
| Fast | 記憶を取りこぼさない   | 原文を簡易処理して高速で保存し、所要時間はミリ秒級で、次の対話ターンですぐ検索できます。             |
| Fine | 近距離の整理   | 現在のコンテキストと履歴記憶をさかのぼり、衝突を発見した場合は元の Memory ID 上に新しいバージョンを生成します。 |
| Offline | グローバル整理 | 定期的に長距離のさかのぼりを行い、初期に認識されなかった衝突を修正して、全体の一貫性を保ちます。                  |

形成される結果は 2 本の衝突する記憶ではなく、**同一の Memory ID における V1 / V2 / V3… の時間進化チェーン** です

<br>

**例**：

```json
# 2025年と仮定
User: 私は小忆です。今は上海に住んでいて、あまり辛いものは食べられません。

# 2026年と仮定
User: 最近成都に引っ越したんですが、急に四川火鍋が大好きになって、辛い鍋が好きです！
```

```json
V1 バージョン記憶：ユーザーの名前は小忆で、上海に住んでおり、辛いものが食べられない
V2 バージョン記憶：ユーザーの名前は小忆で、成都に住んでおり、辛いものが好きで、四川火鍋が好き。
```

>このように、同じ 1 件の記憶は時間とともに進化でき、「信頼できる現在の認識」を提供できると同時に、完全な履歴軌跡も保持します。

<br>

このようにして、最初に述べた問題を解決しました：
- **呼び出しがより効率的**：大規模モデルに連結して渡す際は、洗練された記憶だけを渡せばよく、Token 消費を削減します。
- **検索がより速くより正確**：事実 / 好み / ツール / スキル記憶を直接特定でき、ひとまとまりの生メッセージ全体を対象にする必要がありません。
- **体験がより安定**：モデルはユーザー習慣への理解を継続的に維持でき、コンテキスト喪失によって逸脱することがありません。

<br>

## 2. 応用：より深いカスタマイズをしたい場合

MemOS において、**記憶生成** とは、生の入力をスケジュール可能・検索可能な記憶ユニットへ加工する全過程を指します。具体的なパイプラインの詳細（抽出方法、埋め込みモデル、保存バックエンドなど）は、バージョンやコミュニティの実践に伴って継続的に進化していくため、本節では固定された唯一のフローは提供せず、**拡張可能なポイント** を説明します。必要に応じて、これらの位置で手を加えることができます。

| **拡張可能ポイントの例**      | **デフォルト動作**                                        | **カスタマイズ方法**                                                               |
| ------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------- |
| 抽出と構造化          | デフォルトで MemoryItem（内容、タイムスタンプ、ソースなどを含む）を生成します | 抽出モデルまたはテンプレートを置き換えるか、schema にドメインフィールドを追加できます                         |
| 分割と埋め込み            | システムは長文を分割して埋め込みモデルに送ります                  | 分割粒度を調整するか、より適した embedding モデル（bge、e5 など）に置き換えることができます            |
| 保存バックエンド              | デフォルトではベクトルデータベース（Qdrant など）を使用します                   | グラフデータベースに切り替えるか、両者を組み合わせて使用できます                                           |
| マージとガバナンス            | システムは重複と衝突を自動処理します                            | カスタムルール（時間優先、ソース優先など）を作成できます |
