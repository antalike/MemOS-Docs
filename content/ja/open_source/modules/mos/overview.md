desc: MemOS v2.0 は、よりモジュール化され、疎結合なアーキテクチャを採用しています。旧版の MOS クラスは廃止され、現在は Components (コンポーネント) + Handlers (ハンドラー) のパターンを使用した開発が推奨されています。

このアーキテクチャは、「システムの部品」（Components）と「ビジネスロジックの実行」（Handlers）を分離し、システムをより拡張、テスト、保守しやすくします。

## 1. コアコンセプト

### 1.1 Components (コアコンポーネント)

Components は MemOS の各「器官」であり、サーバー起動時に初期化され（`init_server()` を通じて）、ライフサイクル全体で再利用されます。

コアコンポーネントには以下が含まれます：

#### コアメモリコンポーネント

1. **MemCube**: メモリコンテナ。異なるユーザー/異なるアプリケーションシナリオのメモリを分離し、多様なメモリモジュールを一元管理するために使用されます.  
2. **MemReader**: メモリ処理器。ユーザー入力の各種素材（チャット、ドキュメント、画像）を、システムに書き込み可能なメモリ断片として解析します.  
3. **MemScheduler**: バックグラウンドスケジューラ。バックグラウンドタスクキューの管理を担当し、メモリの保存、インデックス作成、整理などの時間のかかる操作を非同期で処理し、マルチタスクの並列実行をサポートします.  
4. **MemChat**: 対話コントローラ。対話過程で自動的に「メモリ検索 -> コンテキスト管理 -> LLM スケジューリング -> メモリ更新」の対話ループを実行する責任を持ちます.  
5. **MemFeedback**: メモリ訂正器。ユーザーの自然言語フィードバックを自動的に理解し、競合するメモリを正確に特定して原子的な修正（訂正/補足/置換）を実行します.

### 1.2 Handlers (業務ハンドラー)

Handlers は MemOS の「頭脳」であり、具体的なビジネスロジック（追加、検索、対話など）をカプセル化し、Components （器官）の各種能力を呼び出して連携させることで、具体的なユーザータスクを完了します。

#### コア Handler 概要

| Handler | 役割 | コアメソッド |
| :--- | :--- | :--- |
| **AddHandler** | メモリ追加 (対話/ドキュメント/テキスト) | `handle_add_memories` |
| **SearchHandler** | メモリ検索 (セマンティック検索) | `handle_search_memories` |
| **ChatHandler** | 対話 (メモリ拡張付き) | `handle_chat_complete`, `handle_chat_stream` |
| **FeedbackHandler** | フィードバック (メモリ修正/手動介入) | `handle_feedback_memories` |
| **MemoryHandler** | 管理 (詳細取得/削除) | `handle_get_memory`, `handle_delete_memories` |
| **SchedulerHandler** | スケジューリング (非同期タスク状態の照会) | `handle_scheduler_status`, `handle_scheduler_wait` |
| **SuggestionHandler** | 提案 (推奨質問の生成) | `handle_get_suggestion_queries` |

## 2. API 詳解

### 2.1 初期化 (Initialization)
初期化はシステム起動の基盤です。すべての Handler の実行は、統一されたコンポーネント登録と依存性注入メカニズムに依存しています。

- コンポーネント読み込み ( init_server ) : システム起動時に、LLM（大規模言語モデル）、ストレージ層（ベクトルデータベース、グラフデータベース）、スケジューラ（Scheduler）、および各種 Memory Cube を含むすべてのコアコンポーネントが初期化されます。
- 依存性注入 ( HandlerDependencies ) : コードの疎結合性とテスト可能性を保証するため、すべてのコンポーネントは依存コンテナ（`HandlerDependencies`）に統一してカプセル化されます。Handler が起動する際は、このコンテナを受け取るだけで、必要な `naive_mem_cube`、`mem_reader`、`feedback_server` などのリソースを取得でき、各自でこれらのコンポーネントを重複して作成する必要はありません。

### 2.2 メモリ追加 (AddHandler)
AddHandler は頭脳の"メモリ受け入れ命令"であり、外部情報を変換してシステムメモリに書き込むことを担当します。各種情報の受け入れと変換を担当するだけでなく、フィードバックを自動識別して専用のフィードバック処理フローにルーティングすることもできます。

- コア機能 :
  - マルチモーダル対応 : ユーザー対話、ドキュメント、画像など、さまざまな入力形式を処理し、統一してシステム内部のメモリオブジェクトに変換できます。
  - 同期および非同期モード : `async_mode` パラメータにより処理方式を制御します。**同期モード**（"sync"）：即時処理され、呼び出し元は結果を待機してブロックされ、デバッグに適しています；**非同期モード**（"async"）：タスクはバックグラウンドキューに投入され、MemScheduler により並列処理され、API は即座にタスク ID を返し、本番環境での応答速度向上に適しています。
  - 自動フィードバックルーティング : リクエストで `is_feedback=True` が指定されている場合、Handler は対話内の最後のユーザーメッセージをフィードバック内容として自動抽出し、通常の新規メモリ追加としてではなく、MemFeedback に転送して処理します。
  - マルチターゲット書き込み : 複数の MemCube への同時メモリ書き込みをサポートします。複数の対象 Cube が指定されている場合、システムはすべての書き込みタスクを並列処理します；対象が 1 つ בלבד の場合は、軽量な処理方式を使用します。

### 2.3 メモリ検索 (SearchHandler)
SearchHandler は頭脳の"メモリ検索命令"であり、セマンティクスベースのインテリジェントなメモリクエリ能力を提供し、RAG（検索拡張生成）を実現するための重要なコンポーネントです。

- コア機能 :
  - セマンティック検索 : ベクトル埋め込み（Embedding）技術を利用し、クエリ文の意味的類似度に基づいて関連メモリをリコールします。単純なキーワードマッチングと比べて、ユーザー意図をより正確に理解できます。
  - 柔軟な検索範囲 : 検索対象のデータ範囲を指定することをサポートします。たとえば、特定ユーザーのメモリライブラリ内のみを検索することも、複数ユーザーにまたがって共有公開メモリを検索することもでき、異なるプライバシーおよび業務ニーズを満たします。
  - 複数の検索モード : アプリケーションシナリオに応じて、速度と精度の間で柔軟に選択します。**高速モード**はリアルタイム性が高いシナリオに適し、**精細モード**は高いメモリ精度を追求するシナリオに適し、**ハイブリッドモード**はその両方を兼ね備えます。
  - 多段推論検索 : 複雑な問題に対して、深い推論能力の導入をサポートし、多ラウンドの理解と検索を通じて最も関連性の高いメモリに段階的に近づきます。

### 2.4 対話 (ChatHandler)
ChatHandler は頭脳の"対話調整命令"であり、ユーザーの対話ニーズを完全な業務フローに変換することを担当します。データを直接保存するのではなく、他の Handler を調整することでエンドツーエンドの対話タスクを完了します。

- コア機能 :
  - フローオーケストレーション : "メモリ検索 → LLM 生成 → メモリ保存" の完全な対話ループを自動実行します。ユーザーの質問は毎回、履歴メモリに基づいてよりスマートな応答を得られ、同時に各対話は新たなメモリとして蓄積され、対話そのものが学習となります。
  - コンテキスト管理 : history （履歴対話）と query （現在の質問）の連結処理を担当し、LLM が完全な対話文脈を理解できるようにして、情報損失を防ぎます。
  - 複数のインタラクションモード : 標準的なリクエスト-レスポンスモード（ APIChatCompleteRequest ）とストリーミング応答（Stream）モードをサポートします。標準モードは単純な問題に適し、ストリーミングモードは長文応答に適しており、異なるフロントエンドのインタラクションニーズを満たします。
  - メッセージプッシュ（オプション） : 応答生成後に結果を自動的にサードパーティプラットフォーム（DingTalk など）へプッシュすることをサポートし、マルチチャネル統合を実現します。

### 2.5 フィードバックと修正 (FeedbackHandler)
FeedbackHandler は頭脳の"フィードバック修正命令"であり、AI の動作に対するユーザーの自然言語フィードバックを理解し、関連するメモリ内容を自動的かつ正確に特定して修正することを担当します。

- コア機能 :
  - メモリ修正 : ユーザーが AI の誤りを指摘した場合（例："会議場所は北京ではなく上海です"）、Handler は関連する古いメモリを自動更新またはマークします。システムは直接削除ではなくバージョン管理を採用し、変更履歴の追跡可能性を保持します。
  - 正負フィードバック : ユーザーが高評価または低評価で特定メモリの品質をマークすることをサポートします。システムはこれに基づいてそのメモリの重みと信頼度を調整し、その後の検索をより正確にします。
  - 正確な特定 : 2 種類のフィードバック方式をサポートします。1 つは対話履歴に基づいて競合情報を自動特定する方式で、もう 1 つはユーザーが具体的なメモリを直接指定して修正する方式であり、フィードバックの有効性と正確性を向上させます。

### 2.6 メモリ管理 (MemoryHandler)
MemoryHandler は頭脳の"メモリ管理命令"であり、メモリデータに対する基盤的な CRUD（作成、削除、更新、照会）能力を提供し、主にシステム管理バックエンドやデータクリーンアップなどの運用シナリオで使用されます。

- コア機能 :
  - 精密管理 : AddHandler の業務レベル書き込みとは異なり、この Handler はメモリ ID を通じて単一メモリの詳細情報を直接取得したり、物理削除を実行したりできます。この直接操作方式はビジネスロジックのラッピングを迂回し、主にデバッグ、監査、またはシステムクリーンアップに使用されます。
  - 基盤直通 : 一部の管理操作では、最高効率かつ最低遅延のデータ操作能力を提供するために、基盤のメモリ器官（naive_mem_cube）と直接やり取りする必要があり、システム運用のニーズを満たします。

### 2.7 タスクスケジューリング状態 (SchedulerHandler)
SchedulerHandler は頭脳の"タスク監視命令"であり、システム内のすべての非同期タスクのリアルタイム実行状態を追跡し、ユーザーがバックグラウンドタスクの進捗と結果を把握できるようにします。

- コア機能 :
  - 状態追跡 : Redis バックエンドと連携して、タスクのリアルタイム状態（Queued キュー待ち中, Running 実行中, Completed 完了, Failed 失敗）を追跡します。
  - 結果取得 : タスク結果照会インターフェースを提供します。非同期タスク完了後、ユーザーはこのインターフェースを通じて最終実行結果またはエラー情報を取得でき、操作が成功したかどうか、および失敗原因を把握できます。
  - 同期待機（デバッグツール） : テストおよび統合テスト時に、非同期タスクを強制的に同期待機へ変換するツールを提供し、開発者が同期コードをデバッグするのと同様に非同期フローをデバッグできるようにして、開発効率を向上させます。

### 2.8 おすすめの質問 (SuggestionHandler)
SuggestionHandler は頭脳の"提案生成命令"であり、ユーザーの潜在的なニーズを予測することで、関連する質問を積極的に推奨し、ユーザーがシステム能力を探索し、興味のあるトピックを発見するのを支援します。

- コア機能 :
  - デュアルモード生成 :
    - 対話ベースの提案 : ユーザーが最近の対話記録を提供した場合、システムは対話コンテキストを分析し、ユーザーが興味を持つ可能性のある後続トピックを推測して、3 つの関連する推奨質問を生成します。
    - ユーザープロファイルベースの提案 : 対話コンテキストがない場合、システムはユーザーの最近のメモリからその関心と状態を推測し、ユーザーの最近の生活または仕事に関連する推奨質問を生成します。これは対話開始時またはトピック切り替え時の使用に適しています。
  - 多言語対応 : 推奨質問はユーザーの言語設定に自動適応し、中国語、英語など複数言語をサポートして、異なるユーザーの体験を向上させます。
