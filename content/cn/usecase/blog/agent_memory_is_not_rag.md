Agent 可以检索政策 PDF、记住客户偏好简洁回答、在工具调用间维持工作流，也可以查询实时订单系统。这是四种不同职责。把它们全部叫作“记忆”，会让生产设计和产品比较失去精度。

RAG 查找当前回答所需的外部证据；Agent 记忆保留跨轮次、会话或工作流的有用状态。更大的上下文窗口为单次推理提供更多材料，但保存什么、如何更新旧偏好、怎样执行删除，仍需要另外定义。Oracle 的开发者指南同样强调：持久记忆需要明确身份与范围、来源、生命周期规则和遵循权限的召回。[Oracle Developers](https://blogs.oracle.com/developers/agent-memory-is-not-rag)

向量索引可以是很好的检索组件。完整记忆方案还需要规定信息何时成为持久记录、怎样纠错、过期、隔离和审计。

选择 AI 记忆方案，先明确需要记住什么、信息在哪里可用，以及它应当怎样随时间变化。不同产品通过记忆 API、时序图谱、有状态 Agent 或更广泛的记忆管理系统处理这些需求。

本文从生命周期、检索、部署与应用适配比较 Mem0、Zep/Graphiti、Letta、MemOS 和 Supermemory，说明 MemOS 的位置，并给出实际选型问题，帮助探索阶段与生产评估中的团队作出决定。

## 先区分四个层次

**提示词上下文**是模型在一次推理中可见的有限 Token 集合，可以包含当前用户消息、系统指令、工具结果、滚动摘要、检索文档与选定记忆。上下文工程关注决策时如何选择、过滤、压缩和刷新这些材料。[Redis](https://redis.io/blog/ai-agent-context/)

**RAG**从文档、记录、表格或其他授权材料中检索证据，主要职责是为回答提供依据：使用相关、可访问且有效的来源，并保留足够的溯源信息供核查。RAG 可以是无状态的。良好的流程会处理租户与 ACL 过滤、文档版本、分块或结构化检索，并在需要证据时提供引用。它适合回答“当前政策怎么规定？”

**向量数据库或向量索引**存储嵌入并支持相似度检索，许多产品还提供过滤、关键词、元数据或混合检索。它可以支撑 RAG 和语义召回。至于昨天改变的语言偏好是否替代旧事实，以及跨会话如何识别用户，属于更上层的记忆管理。

**Agent 记忆**是经过选择、限定范围、供以后使用的持久状态，通常包括偏好、带时间的事实、任务状态、摘要、决策、已学习流程或已验证工具结果。难点包括：保存什么；哪些用户、租户、Agent、任务与权限背景可以检索；什么会更新或使它失效；谁可以检查、纠正、删除和审计。

生产环境中，这些层次通常并存。客服 Agent 可以组合当前指令、任务摘要、限定到客户与租户的记忆、RAG 政策引用，以及工具返回的实时账户状态。业务实时数据仍以业务系统为准。

## MemOS 的位置

我们构建 MemOS，是为了让长期记忆成为 AI 应用和 Agent 中可以管理的组成部分。它提供独立层，保留有用背景、在相关时召回，并随着偏好、事实和任务变化更新，支持跨对话连续性、个性化与 Agent 工作流中的背景复用。

MemOS 将存储、检索、多种记忆形态与记忆调度结合起来。Cloud API 提供对话写入、记忆检索、记录更新与删除，以及通过反馈纠错；过滤、标签、异步处理、知识库与 Chat API 支持不同接入需求。

可以通过托管 Cloud、开源框架与支持的 Agent 集成接入，根据团队运维能力和定制要求选择。

[MemOS 官网](https://memos.openmem.net/) · [Cloud 概述](https://memos-docs.openmem.net/cn/memos_cloud/getting_started/overview/) · [API 概览](https://memos-docs.openmem.net/cn/api_docs/start/overview/) · [GitHub](https://github.com/MemTensor/MemOS)

MemTensor 是 MemOS 背后的公司，为 AI 应用构建记忆基础设施，并研究长期记忆与持续学习，目标是减少幻觉、改善个性化，让系统更好地利用已有经验。

我们的工作覆盖 Memory³ 研究、MemOS、Agent 记忆基础设施与记忆原生基座模型研究，将理论与信息的长期存储、检索和维护结合起来。MemOS 将这一方向带入需要跨对话背景的应用。

## 生产选型的七个维度

比较产品前，先用一页说明允许存储的数据类别、必须隔离的范围、纠错与删除负责人、权威来源，以及记忆不可用时的处理方式，再按以下七个维度评估。

### 1. 生命周期

能否有选择地添加、更新、删除、过期、合并或回滚记忆？应用能否区分原始事件、抽取记忆，以及让它成为持久记录的规则？检查时间、来源、冲突处理、保留控制与明确纠错路径。将每条消息生成向量属于摄入，实现生命周期还需要这些规则。

### 2. 检索与上下文组装

检索返回文档、事实、图关系、属性、记忆块、摘要，还是多种组合？生成前如何过滤？测试租户、用户、Agent、会话、时间、记忆种类与权限条件。同时评估质量与上下文预算：十行相关记忆可能比二十个相似分块更有用。用任务质量、泄露率、检索准确率和新增延迟衡量。

### 3. 部署与数据边界

选择 SDK 前，先确定运行模式。公开文档提供库、自托管服务、托管云服务，还是多种路径？明确模型、嵌入、数据库、图存储、对象存储、遥测与出站网络依赖。自托管软件包之外，还需要设计完整私有部署与企业控制。

### 4. 治理与隔离

将记忆读取作为数据访问决策。在相关场景中，明确租户、用户、Agent、任务或会话、请求和权限标识。摄入前定义脱敏与秘密信息排除规则，在实际采用的产品版本中验证按范围删除、纠错、保留、访问控制和审计证据。Cloudflare 也将限定范围的持久状态视为核心运行问题。[Cloudflare](https://blog.cloudflare.com/introducing-agent-memory/)

### 5. 可观测性

为每轮模型调用记录检索请求、过滤条件、候选 ID、选中记忆 ID、来源、时间、Token 数、模型回复与用户反馈。分别观测接纳、修改、删除和回滚。在减少敏感日志副本的同时，能够解释为什么送入某条记忆，以及旧记录为何仍然存在。

### 6. 生态与应用适配

评估实际会用的 Python、TypeScript、REST、MCP、Agent 框架、工具调用或云平台接口。优先选择能延续现有身份与授权模型的接入路径，并验证集成是否落实组织治理策略。

### 7. 实际环境中的运行成熟度

按自身要求测试升级、备份、灾难恢复、模型供应商故障、限流、模式变化、迁移和事件支持。代码、文档和部署选项的存在，与满足特定 SLA 或合规体系，是不同的验证目标。

## 五种 AI 记忆方案

### Mem0

**概述。** 官方仓库提供记忆库、自托管服务器与托管平台。自托管通过 Docker Compose 部署，文档包含默认启用认证、管理员初始化、API Key 与仪表盘，也提供 Python、npm 安装和按用户 ID 添加、检索的 CLI。仓库使用 Apache-2.0 许可。[Mem0 仓库](https://github.com/mem0ai/mem0) · [自托管说明](https://github.com/mem0ai/mem0/blob/main/docs/open-source/setup.mdx)

**适用场景。** 需要以记忆为中心的接入接口，并希望在库、托管与自托管之间选择的团队。文档化的自托管路径为自行运维提供起点；托管平台是另一种运维选择。

**评估重点。** 检查抽取与检索配置如何处理纠错、冲突、租户隔离、删除传播及自身授权模型。使用自己的模型和数据评估质量与成本，确认 SDK 抽象下实际选中了什么记忆。

### Zep/Graphiti

**概述。** Graphiti 与 Zep 相关，但属于不同选择。Graphiti 是 Zep 的 Apache-2.0 开源时序上下文图框架，仓库包含事件摄入、混合检索、图距离重排、MCP 服务器与图存储选项。Zep 是基于 Graphiti 的托管 Agent 记忆服务，文档描述用户与任务线程、上下文组装，以及 Zep Cloud、BYOK 和 BYOC 等部署治理选项。[Graphiti](https://github.com/getzep/graphiti) · [Zep 与 Graphiti](https://help.getzep.com/zep-vs-graphiti) · [Zep 概念](https://help.getzep.com/concepts) · [安全与合规](https://help.getzep.com/v3/security-compliance)

**适用场景。** 时序关系和图检索是核心，且团队希望构建、运维外围服务时，可以考虑 Graphiti；希望通过托管服务获得同类能力，并使用已文档化的用户、任务线程和企业部署抽象时，可以考虑 Zep。

**权衡。** 使用 Graphiti，需要团队设计图基础设施、抽取、实体消歧、时序失效、并发与授权。Zep 减少部分运维工作，同时引入商业服务、契约和数据边界选择。两种路径都应测试：有时间范围的关系是否足以改善任务，值得承担额外图谱与摄入复杂度。

### Letta

**概述。** Letta 面向有状态 Agent，提供 API、Python 与 TypeScript 客户端、自托管 base URL，以及可挂载或从 Agent 移除的记忆块。官方 Apache-2.0 仓库将其称为开源项目，并提供本地 CLI 与 API 路径。TypeScript 文档介绍了通过挂载到多个 Agent 来共享记忆块。[Letta 仓库](https://github.com/letta-ai/letta) · [TypeScript 文档](https://docs.letta.com/api/typescript)

**适用场景。** 记忆与 Agent 运行时紧密结合，并希望采用以 Agent 为中心的状态模型时，可以考虑 Letta。有意识且经过授权的共享背景，可以通过共享块实现。

**权衡。** 将隔离、记忆块共享、编辑、删除、导出、模型行为、工具状态和迁移作为主要测试用例，确认应用是否需要独立于单个 Agent 运行时的可迁移记忆。

### MemOS

**概述。** MemOS 为 AI 应用与 Agent 提供独立的记忆存储、检索、更新和管理层。Apache-2.0 开源框架支持多种记忆形态与调度；Cloud 提供抽取、检索、更新、删除、反馈纠错，以及知识库与 Chat 能力，也为企业提供私有部署和定制集成选项。[MemOS 仓库](https://github.com/MemTensor/MemOS) · [Cloud 文档](https://memos-docs.openmem.net/cn/memos_cloud/getting_started/overview/) · [API 概览](https://memos-docs.openmem.net/cn/api_docs/start/overview/) · [官网](https://memos.openmem.net/)

**适用场景。** 需要跨对话、跨 Agent 工作流延续背景，并明确控制检索与维护的应用。托管接入可以选择 Cloud API；也可以按运行环境选择开源框架与 Agent 集成。

**权衡。** 测试负载所需的记忆形态与调度行为、每次调用携带的身份和范围、纠错与删除的生命周期、集成适配，以及所选版本的运维设计。广泛的记忆抽象带来灵活性，也要求明确哪些信息可以成为可复用记忆。

### Supermemory

**概述。** 官方 MIT 许可仓库提供记忆与上下文 API、JavaScript 与 Python SDK、容器标签、文档摄入、语义和混合检索，以及 API Key 认证。公开仓库的自托管快速开始包含本地服务器和嵌入式引擎，SDK 可以连接自托管 base URL。[仓库](https://github.com/supermemoryai/supermemory) · [自托管快速开始](https://github.com/supermemoryai/supermemory/blob/main/apps/docs/self-hosting/quickstart.mdx) · [SDK 文档](https://github.com/supermemoryai/supermemory/blob/main/apps/docs/integrations/supermemory-sdk.mdx)

**适用场景。** 希望采用 API 接入，将用户背景与文档检索结合，并评估托管式调用和已文档化的本地、自托管路径的团队。

**权衡。** 检查容器标签如何映射租户、用户、Agent 与会话边界。测试属性或抽取记忆的时效、文档与记忆检索的区别、删除传播、模型供应商依赖，以及实际负载下自托管设计的规模与持久性。

## 从比较走向决策

产品适配取决于记忆形态。图优先系统适合随时间变化的关系，Agent 运行时系统适合有状态控制，记忆 API 适合快速接入，更广泛的记忆操作层适合多种形态间的生命周期与调度。

按自己的数据规则开展限定时间的概念验证。按需为请求提供租户、用户、Agent、任务、会话与请求标识，准备已知正确事实、故意过期事实、冲突更新、排除保留的敏感值，以及跨租户近似记录。衡量检索准确率、任务成功率、延迟、Token 成本、写入成本、删除完成情况，以及解释选中条目的难易程度，并演练供应商故障与恢复。

当团队能解释每条记忆的归属、保存原因、替代关系、访问权限、存储位置、观测与删除方式时，选型才具备生产依据。RAG 则继续承担来源明确的证据检索，与持久 Agent 状态协同工作。
